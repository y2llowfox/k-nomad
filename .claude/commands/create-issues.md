## Context

생성할 이슈 소스: $ARGUMENTS

## 역할

너는 **GitHub 이슈 생성 전문가**다. 작업 계획(PLAN.md 등)이나 사용자 설명을 기반으로 구조화된 GitHub 이슈를 생성한다.

## 실행 절차

### 1. 입력 분석

`$ARGUMENTS`를 분석하여 이슈 소스를 파악한다.

- **파일 경로인 경우** (예: `PLAN.md`, `docs/spec.md`): 해당 파일을 읽어서 Phase/작업 단위를 추출
- **텍스트 설명인 경우**: 설명을 분석하여 이슈 목록 도출
- **불명확한 경우**: 프로젝트 루트의 `PLAN.md`를 기본으로 사용

### 2. 사전 확인

이슈를 생성하기 전에 다음을 확인한다:

- `gh auth status`로 GitHub 인증 상태 확인
- `git remote -v`로 원격 저장소 확인
- 기존 이슈 목록(`gh issue list`)을 확인하여 중복 방지

### 3. 이슈 구조화

각 이슈는 다음 형식을 따른다:

**제목**: `[Phase N] 작업 제목` (간결하고 명확하게)

**본문**:
```markdown
## 오버뷰
이 이슈에서 무엇을 하고, 완료되면 어떤 상태가 되는지.

## 선행 조건
- 이전 이슈/Phase 의존성 (있으면)

## 작업 체크리스트
- [ ] 작업 항목 1
- [ ] 작업 항목 2

## 검증 체크리스트
- [ ] 검증 항목 1
- [ ] 검증 항목 2
```

### 4. 이슈 생성

- `gh issue create`로 이슈를 생성한다
- 가능하면 라벨을 추가한다: `enhancement`, `bug`, `documentation` 등
- Phase 간 의존성이 있으면 본문에 이슈 번호를 상호 참조한다
- 생성된 이슈 목록을 사용자에게 보여준다

### 5. 생성 후 처리

- 모든 이슈가 생성되면 이슈 번호 + 제목 + URL 목록을 정리하여 출력
- PLAN.md에 이슈 번호를 매핑하여 업데이트할지 사용자에게 확인

## 이슈 생성 원칙

1. **1 Phase = 1 이슈**: 작업 계획의 Phase 단위로 이슈를 생성한다 (너무 세분화하지 않는다)
2. **자급자족**: 이슈 본문만 보고 작업 가능하도록 충분한 맥락을 포함한다
3. **의존성 명시**: 선행 이슈가 있으면 `Depends on #N` 형태로 참조한다
4. **중복 방지**: 기존 이슈와 겹치는 내용이 있으면 생성하지 않고 사용자에게 알린다
5. **순차 생성**: 이슈 번호가 순서대로 매겨지도록 하나씩 생성한다 (상호 참조를 위해)
